## Hallazgos

### 1. P2 — Se recorta el remoto antes de quitar sus credenciales

**Referencia:** `src/repo-local.ts:59–64`, especialmente `:60`; la salida se incorpora al mensaje en `src/repo-local.ts:124`.

**Qué pasa.** `origenParaMostrar` hace `url.trim().slice(0, 200)` antes de eliminar `usuario:clave@`. Si el `@` está después del carácter 200, el texto recortado ya no parece tener credenciales: la expresión regular lo devuelve con el usuario y una parte de la clave. No cumple la garantía de no mostrar las credenciales del `origin`.

**Escenario concreto.** Un clon tiene un remoto HTTPS con una credencial larga. `guide check --repo o/r`, `guide publish --repo o/r` o `install record --repo o/r` no pueden asociarlo a GitHub y muestran el mensaje de clon incompatible. Ese mensaje ahora incluye parte de la credencial; queda en la pantalla, en los registros o en el contexto del asistente. No hace falta una llamada al motor.

**Reproducción ejecutada, sólo con valores ficticios y sin escrituras:**

```js
origenParaMostrar(
  'https://alice:' + 'fake-secret'.repeat(25) + '@github.com/o/r.git'
)
// https://alice:fake-secretfake-secretfake-secret...fake-secre
```

También ejecuté `repoPedido` con un doble de git que devuelve `https://alice:` + `'FAKE_TOKEN_'.repeat(25)` + `@gitlab.com/o/r.git`, y `flagRepo: 'o/r'`. Su `sinClon` contiene:

```text
This clone is `https://alice:FAKE_TOKEN_FAKE_TOKEN_...`, which I can't tie to github.com/o/r. ...
```

El remoto corto de control (`https://alice:fake-secret@github.com/o/r.git`) sí se sanea correctamente. El test actual de `test/repo-local.test.ts` sólo cubre credenciales cortas.

**Arreglo propuesto.** Quitar las credenciales de la URL completa y **recién después** limitar el tamaño de lo que se muestra. Si no se puede interpretar con seguridad su autoridad, mostrar un marcador neutro, no la entrada cruda. Agregar regresiones con el `@` antes, en el límite y después del carácter 200, tanto en el helper como en el mensaje final de un comando que exige clon.

### 2. P2 — `project show` no aplica el freno de cuenta antes del paso de conexión

**Referencia:** `src/comandos/proyecto.ts:218–222`; contraste con `src/comandos/proyecto.ts:116–119` y `src/comandos/contexto.ts:111–125`. El POST de conexión se inicia en `src/comandos/repo-conectar.ts:85`.

**Qué pasa.** `project show` ya consulta `/api/yo`, pero, si no encuentra proyecto, devuelve 0 sin llamar a `coherenciaAlCrear`. Sólo `project create` produce `dueno_distinto_del_login` y `sin_github`. Esto contradice la explicación del pedido de revisión de que esos motivos se calculan en `show` y `create`, y deja incompleta la prevención antes del navegador que busca la fricción 6.

**Escenario concreto.** Sin archivo de proyecto en el clon, el repo es `dueno-a/app` y la clave muestra `dueno-b`. La skill empieza por `project show`; recibe 0 y `proyecto: null`, por lo que sigue con `repo connect --start` antes de llegar a `project create`. El pedido de conexión ya se creó y la persona puede haber pasado por el navegador cuando aparece el freno. Con una cuenta por email, el `show` también da 0 y el rechazo llega en la conexión del motor, no en el chequeo temprano de la terminal.

**Reproducción ejecutada con las funciones reales y dobles sin red ni disco:**

```text
repo = dueno-a/app; usuario.login = dueno-b; equipo = tnt_b
buscarProyecto -> null; archivos.leer -> null

project show   -> 0, contexto.identidad=dueno-b, proyecto=null
repo connect   -> 5, llamadas=["POST /api/conexiones"]
project create -> 4, motivo=dueno_distinto_del_login
```

El `POST` anterior es un **contador del doble**, no una operación real. La evidencia guardada por el autor confirma el mismo hueco: `docs/verificaciones/2026-10-29-1a1-terminal-salidas.txt`, bajo «(4) sin archivo del clon», muestra `project create` con 4 y el `show` siguiente con 0 para `dueno-b`/`dueno-a`.

Lo contrasté con el recorrido de `skills/supcoflow/SKILL.md` en `fm/e1-skill` (`49239ed`), paso 2: con proyecto ausente se conecta **antes** de crear. El plan conserva ese orden e introduce el `show` como control inicial. En el motor, `app/api/conexiones/route.ts:30–33` rechaza la cuenta sin GitHub o crea el pedido; no hay un control temprano equivalente por login.

**Arreglo propuesto.** En `project show`, cuando `encontrado === null`, reutilizar `coherenciaAlCrear` con el `yo` que ya se consultó y devolver el mismo 4 antes de ofrecer continuar. Mantener las excepciones ya diseñadas: con proyecto existente no comparar dueños; con clave de consulta no comparar logins. Agregar pruebas de `show` para dueño distinto y email, y una prueba del recorrido `show → connect` que compruebe que no se inicia conexión tras ese 4. No hace falta agregar `/api/yo` a los pedidos parciales ni otra llamada a `show`.

## Qué verifiqué que está bien

### T1 — Protección de git

- El cambio está en un envoltorio del almacén, no sólo en el primer guardado: `src/guardado/protegido.ts:26–34` protege `escribir` y `borrar`. La salida temprana de `borrar` sólo ocurre si no hay entrada que borrar, por lo que el almacén base no reescribe nada.
- `src/entorno.ts:436–451` usa ese envoltorio para **ambos** registros. `abrir`, `confirmar` y `descartar` de pruebas pasan por su escritura; `olvidar` de idempotencia pasa por `borrar` y avisa si no puede protegerlo.
- `asegurarProteccionDeGit` crea el `.gitignore` en exclusiva, no edita uno previo y vuelve a consultar git. Comprueba el archivo y su `.tmp`; sólo el código 0 de `check-ignore` permite guardar. Los errores no se convierten en éxito.
- La búsqueda considera la ruta escrita y la real. El caso de un enlace bajo un repo y destino en otro falla cerrado si git rechaza la ruta que atraviesa el enlace; el test real lo declara expresamente. No se promete que toda disposición con `stow` funcione.
- Ejecuté comprobaciones en memoria con códigos de git `0`, `1`, `2`, `128` y `null`: sólo 0 dejó llegar a las mutaciones del almacén; con 0 se consultaron archivo y temporal. El prechequeo sin `.gitignore` no llamó a ninguna operación de escritura.
- `git diff 19d210b..8f7cf78 -- src/guardado/index.ts` está vacío. Las credenciales siguen con el guardado anterior, sin esta excepción.
- Inspeccioné los tests con disco/git reales de `test/proteccion-de-git.test.ts`: archivos nuevos, seguidos, sólo agregados, `.tmp` seguido, `.gitignore` previo, enlaces y limpieza de idempotencia. **No repetí esos tests en esta revisión de sólo lectura.**
